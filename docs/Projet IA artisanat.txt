I- Description des Composants Adaptés au Nouveau Contexte

1. Interface Utilisateur (Le "Gemini des Artisans")
Interface de Chat : Similaire à l'interface de Gemini ou Claude, optimisée pour mobile, permettant de poser des questions vocales ou textuelles.
Jauge de Quota (Visibilité) : Un indicateur clair en haut de l'écran affichant "Recherches restantes" ou "Temps d'utilisation PRO restant".
Tunnel de conversion : Un bouton "Passer en illimité / Recharger" qui déclenche directement le prompt USSD ou l'API Mobile Money de l'utilisateur.

2. Le "Rate Limiter" (Le Gardien du Freemium)
C'est la pièce maîtresse pour gérer le modèle économique.
Chaque requête envoyée par un artisan passe d'abord par ici. Le système vérifie dans un cache ultra-rapide (comme Redis) si l'utilisateur Free 
a encore des crédits pour la journée/semaine, ou si l'utilisateur Premium a un abonnement actif.
Si le quota est dépassé, l'API bloque la requête IA et renvoie un signal à l'application mobile pour afficher le pop-up de paiement.

3. Le Moteur IA & RAG (Filtrage par Métier)
Puisque l'IA s'adresse à des artisans très variés, la base de données vectorielle doit être compartimentée.
- Ingestion des connaissances : Alimentez la base (Qdrant ou Pinecone) avec des manuels, des normes, et des fiches techniques.
- Métadonnées par métier : Chaque document vectorisé reçoit un tag (ex: secteur: "artisanat_art", metier: "maroquinerie" ou metier: "menuiserie").
- Filtrage Dynamique : Quand un menuisier pose une question sur "le traitement du bois contre l'humidité", le système RAG ne cherche que dans l'espace vectoriel tagué "menuiserie". 
Cela garantit des réponses ultra-précises et évite que l'IA ne confonde les techniques d'un maçon avec celles d'un sculpteur.

4. Microservice de Quotas & Paiement (Le Modèle Économique)
Pour répliquer le modèle Gemini/Anthropic avec du Mobile Money, deux approches à gérer ici :
- Le Modèle "Crédits" (Pay-as-you-go) : L'utilisateur achète un pack de recherches (ex: 500 FCFA pour 50 requêtes expertes). Idéal pour un usage ponctuel.
- Le Modèle "Durée" (Abonnement SaaS) : L'utilisateur paie un accès illimité (ou avec un plafond haut) pour une durée définie (ex: 2000 FCFA pour 1 mois).
- Gestion des Webhooks : Quand le paiement Mobile Money est validé, l'opérateur envoie une confirmation (Webhook) à ce microservice, qui met instantanément à jour 
le statut de l'artisan en "Premium" dans la base de données.

5. Le Schéma de Base de Données
Pour supporter cette architecture, la base relationnelle (PostgreSQL) doit se concentrer sur l'accès et la catégorisation :

- Table Utilisateurs :

id, telephone, metier_id, sous_metier_id, type_abonnement (Enum: FREE, PREMIUM_TEMPORAIRE).

- Table Quotas_Utilisateurs :

user_id

requetes_restantes_gratuites (Réinitialisé chaque mois ou semaine)

date_fin_premium (Timestamp, si l'artisan a payé pour une durée)

- Table Metiers_Sous_Metiers :

Pour structurer l'arborescence (ex: Bâtiment -> Électricité -> Basse Tension).

- Table Transactions_Mobile_Money :

id_transaction, user_id, montant, operateur (Wave, Orange, etc.), statut_paiement, type_achat (Pack requêtes ou Abonnement temps).

6. Flux d'une Requête Utilisateur "Free" vers "Pro"
Un électricien (profil Free) a épuisé ses 5 questions gratuites de la semaine. Il pose une 6ème question sur les normes de câblage.
Le Rate Limiter intercepte la requête, vérifie la table Quotas_Utilisateurs, et bloque l'action.
- L'application affiche : "Vous avez atteint votre limite gratuite. Débloquez 1 mois d'accès Pro pour 1000 FCFA".
L'artisan clique, saisit son numéro, valide sur son téléphone via Mobile Money. Le Microservice de Paiement reçoit le succès, met à jour la 
date_fin_premium à J+30. L'application se débloque en temps réel (via WebSockets ou polling court) et relance automatiquement la question de l'artisan à l'IA.

II- Définition structurée de la logique des quotas pour la plateforme. 
Pour s'adresser efficacement aux artisans, la mécanique doit être transparente, culturellement adaptée aux habitudes de consommation numérique 
similaire aux "pass" internet), et techniquement robuste pour protéger la rentabilité.

1. L'Unité de Mesure : "Requêtes" vs "Tokens"
Il est crucial de séparer ce que l'utilisateur voit de ce que le système calcule en arrière-plan.
- Front-end (Côté Artisan) : L'unité de mesure est la "Question" (ou "Requête"). Un maroquinier à Bingerville ou un éleveur de volaille ne comprendra pas un 
solde de "4000 tokens". Il doit voir : Il vous reste 3 questions gratuites aujourd'hui.
- Back-end (Côté Serveur) : Le système compte les "Tokens". C'est essentiel car une réponse longue coûte plus cher qu'une réponse courte. 
Le système doit définir une limite maximale de tokens par réponse pour éviter qu'une seule question gratuite ne draine le budget de l'API LLM.

2. Les Paliers de Consommation (Le Modèle Freemium)
Le modèle par "Pass" (inspiré de la vente de data mobile) est le plus adapté pour une conversion rapide via Wave ou Orange Money.
- Le Palier "Découverte" (Gratuit) : Volume : 3 à 5 questions par jour (ou par semaine).
Logique : Les compteurs sont remis à zéro automatiquement (ex: tous les jours à minuit). Cela crée une habitude d'utilisation.
Contrainte technique : Les réponses générées dans ce palier peuvent être artificiellement tronquées ou résumées pour économiser les tokens, 
avec un message d'incitation : "Pour voir les étapes détaillées du schéma de câblage, passez au Pass Pro."
- Le Palier "Pro" (Les Pass Payants via Mobile Money) : Pass 24h (L'urgence chantier) : Ex: 500 FCFA. Donne un accès illimité (avec un Fair Use caché, ex: 100 questions max pour éviter les abus) 
pendant 24 heures. Idéal pour un artisan bloqué sur un problème technique précis.
Pass Mensuel (L'accompagnement continu) : Ex: 3000 FCFA. Accès garanti tout le mois.
Pass "Projet" (Paiement à l'acte) : L'artisan achète un pack de 50 questions valables à vie, qu'il consomme à son rythme.

3. Architecture Technique de la Gestion des Quotas
Pour éviter la latence à chaque message, la base de données principale (PostgreSQL) ne doit pas être interrogée à chaque frappe au clavier.
- Le Cache (Redis) en première ligne : Lorsqu'un artisan se connecte, son quota restant est chargé de PostgreSQL vers Redis.
Chaque fois qu'il pose une question, Redis décrémente instantanément le compteur de 1.
Si Redis indique 0, le système bloque la requête avant même de l'envoyer au LLM (coût zéro pour vous).
- Mise à jour asynchrone : Une tâche de fond met à jour PostgreSQL depuis Redis toutes les X minutes pour garder une trace durable, ou immédiatement lors 
d'un paiement Mobile Money.
- Le Time-To-Live (TTL) : Pour les utilisateurs gratuits, la clé Redis est configurée pour expirer à minuit. À sa suppression, le quota se réinitialise 
automatiquement au prochain appel.

4. Le Parcours UX de la Jauge et du Blocage (Le "Paywall")
L'expérience de restriction doit être pensée non pas comme une punition, mais comme une opportunité d'achat impulsif et fluide.
- Visibilité : La barre de saisie de texte indique : "Posez votre question (2 recherches restantes)".
- L'Alerte (80% d'utilisation) : Lorsqu'il ne reste qu'une question, un léger indicateur visuel (changement de couleur en orange) prévient l'artisan.
- Le Blocage (Hard Stop) : L'artisan pose sa question. La bulle de l'IA s'affiche mais au lieu de la réponse, le composant renvoie un écran de paiement natif.
Texte suggéré : "Vous avez posé une excellente question sur les proportions de ciment. Pour lire la réponse détaillée de l'IA, débloquez un Pass 24h."
- Le Paiement sans friction : Un bouton "Payer 500F avec Wave/Orange Money". Le paiement s'effectue via USSD push ou l'application de l'opérateur, et la réponse de l'IA s'affiche automatiquement dès la confirmation du webhook.

III- structurer la base de connaissances pour optimiser le modèle RAG (Retrieval-Augmented Generation).

1. L'Architecture de la Base Vectorielle
Au lieu de créer une base de données séparée pour chaque métier (ce qui serait coûteux et complexe à maintenir), la meilleure approche consiste à utiliser un 
Index Unique avec Filtrage par Métadonnées (Metadata Filtering). Chaque morceau de texte (ou "Chunk") stocké dans la base possèdera une "carte d'identité" 
sous forme de métadonnées.

Exemple de Métadonnées (Taxonomie)
Chaque document vectorisé devra être accompagné d'un fichier JSON structurant son contexte :

JSON
{
  "secteur_id": "artisanat_art",
  "metier_id": "maroquinerie",
  "categorie_competence": "finition",
  "type_document": "fiche_technique",
  "titre_source": "Guide pratique du travail du cuir",
  "niveau_expertise": "intermediaire",
  "mots_cles": ["cuir", "tannage", "teinture", "finition"]
}
Pourquoi c'est crucial ? Lorsqu'un utilisateur pose une question, le backend récupère son metier_id depuis son profil (ex: maroquinerie) et applique un 
pré-filtre strict ("Ne cherche QUE dans les vecteurs où metier_id = maroquinerie"). Le LLM n'a ainsi accès qu'aux informations pertinentes pour ce métier précis.

2. La Stratégie de Découpage (Chunking)
Un manuel PDF de 200 pages ne peut pas être envoyé d'un coup au LLM. Il faut le découper en petits blocs ("chunks") de texte. Pour des fiches techniques 
artisanales, il faut éviter le découpage aveugle au nombre de caractères.
Privilégiez le Chunking Sémantique ou Structurel : 
Mauvais découpage : Couper le texte tous les 500 mots. Cela risque de couper une étape de fabrication en plein milieu ("Étape 3 : Appliquez le vernis puis... [FIN DU CHUNK]").
Bon découpage : Découper par sections logiques (Titres, Sous-titres, Paragraphes). 
Un "chunk" doit contenir une idée ou une méthode complète (ex: Tout le paragraphe sur le dosage du ciment hydrofuge en maçonnerie).
Conseil : Gardez une taille de chunk d'environ 500 à 1000 "tokens" et prévoyez un chevauchement (overlap) de 10% à 15% entre deux chunks pour ne pas perdre le contexte.

3. Typologie des Données à Ingester
Pour que l'IA soit perçue comme un véritable "Copilote Expert", la base doit contenir des documents variés et qualitatifs, classés par type_document :
- Les Normes et DTU (Documents Techniques Unifiés) : Les règles de l'art (sécurité électrique, normes de construction, résistance des matériaux).
- Guides de Bonnes Pratiques : Techniques de base et avancées (ex: techniques d'assemblage en menuiserie, préparation des supports en peinture).
- Fiches Produits/Matériaux : Caractéristiques des intrants (temps de séchage d'une colle, types de bois, spécificités des tissus).
- Dépannage & Résolution de problèmes (Troubleshooting) : Formats "Problème -> Cause -> Solution" (ex: "Pourquoi mon enduit fissure-t-il au séchage ?").
- Guides de Gestion & Stratégie : Comment chiffrer un devis, comment gérer sa relation client, ou comprendre les possibilités d'accompagnement financier (microfinance).

4. Le Flux d'Exécution du RAG (Comment l'IA utilise la base)
Processus techniquement en une fraction de seconde lorsqu'un artisan interroge l'application :
- La Requête : Un maçon sur un chantier ouvre l'application et demande : "Quel dosage de ciment dois-je utiliser pour une fondation en zone très humide ?"
- Enrichissement (Backend) : Votre API reçoit la question. Elle identifie que l'utilisateur a le metier_id = maconnerie.
- Recherche Vectorielle (Pinecone / Qdrant) : La base vectorielle applique le filtre métadonnée : metier_id == maconnerie.
Elle compare l'embedding de la question avec la base et trouve les 3 "chunks" de texte les plus pertinents parlant des dosages pour fondations humides.
- Construction du Prompt Système : Le backend crée un prompt caché pour le LLM : "Tu es un expert en maçonnerie. Réponds à la question de l'artisan en utilisant
uniquement le contexte suivant. Si l'information n'y est pas, dis que tu ne sais pas."
Contexte récupéré : [Texte du chunk 1], [Texte du chunk 2]
Question : Quel dosage de ciment...
- Génération (OpenAI / Claude) : Le LLM rédige la réponse structurée et l'envoie sur le mobile de l'artisan.

5. Maintenir et Améliorer la Base (Feedback Loop)
L'avantage de cette architecture SaaS est que l'outil s'améliore avec le temps :
- Le bouton "Pouce en l'air / Pouce en bas" : À chaque réponse, l'artisan peut noter la qualité. Si une réponse est mal notée, 
l'équipe technique peut consulter le log pour voir quels documents (chunks) ont été utilisés par l'IA et corriger la base de connaissances si elle est obsolète ou erronée.
- Mise à jour granulaire : Si une norme change (ex: nouvelle norme électrique), vous n'avez pas besoin de réentraîner l'IA. Il suffit de supprimer 
l'ancien document vectorisé de la base et d'uploader le nouveau. L'IA sera instantanément à jour.

IV- Définition complète de la logique métier, technique et utilisateur du paywall pour ProsArtisan.

1. La Logique d'Interception (Backend)
Le paywall n'est pas qu'un simple écran, c'est avant tout un mécanisme de sécurité côté serveur. L'application mobile ne doit jamais décider seule si elle 
affiche ou non la réponse de l'IA (sinon, l'application pourrait être facilement piratée).
- Le Statut HTTP 402 : Lorsqu'un artisan envoie une question, l'API Gateway interroge Redis (le cache des quotas). Si le solde de requêtes est à 0 et 
qu'aucun abonnement n'est actif, le serveur refuse de transmettre la question au LLM. Il renvoie immédiatement à l'application mobile un code HTTP 402 (Payment Required).
- La Charge Utile (Payload) de la réponse 402 : Le serveur ne renvoie pas juste une erreur, il renvoie le contexte de l'offre.

JSON
{
  "statut": "erreur",
  "code": 402,
  "message": "Quota gratuit épuisé.",
  "offres_disponibles": [
    {"id": "pass_24h", "nom": "Pass 24H Urgence", "prix": 500},
    {"id": "pass_mois", "nom": "Pass Mensuel Pro", "prix": 3000}
  ]
}
2. Le Parcours UX : L'Écran du Paywall
Lorsque l'application mobile intercepte le code 402, l'interface de chat bascule instantanément.
- Maintien du Contexte : La question que l'artisan vient de taper reste affichée dans le chat. Elle n'est pas effacée. Cela le rassure : "L'application n'a pas planté, ma question est en attente".
- L'Affichage du Mur : Un composant (type "Bottom Sheet" ou "Carte superposée") glisse par-dessus la zone de réponse de l'IA.
- Le Message de Vente (Copywriting empathique) : À éviter : "Erreur. Payez pour continuer."
- À privilégier : "Vous posez d'excellentes questions ! Pour lire la réponse détaillée de notre IA experte et débloquer toutes les fiches techniques, 
passez à la version Pro."
- L'Appel à l'Action (CTA) : Les boutons de paiement Mobile Money doivent être énormes, clairs et afficher les logos de confiance (Wave, Orange, MTN, Moov).

3. Le Flux de Transaction Mobile Money (Le Cœur du Système)
Pour garantir une conversion maximale, le paiement doit se faire en "Seamless" (sans quitter l'application ProsArtisan). 
Voici la chorégraphie technique, à utiliser par exemple un agrégateur (comme CinetPay, TouchPay) ou l'API directe de Wave Business :
- Étape A : L'Intention de paiement. L'artisan clique sur "Payer 500 FCFA avec Wave". 
L'application mobile envoie une requête à votre backend : "Crée une transaction pour l'utilisateur X, montant 500".
- Étape B : L'Appel à l'Opérateur. Votre backend contacte l'API de paiement et reçoit une URL de paiement ou déclenche un "USSD Push" 
(une notification directe sur le téléphone de l'artisan).
- Étape C : La Validation (Côté Artisan). L'artisan tape son code secret à 4 chiffres sur son téléphone pour valider le retrait depuis son compte Mobile Money.
- Étape D : Le Webhook (Asynchrone). L'opérateur Mobile Money (ou l'agrégateur) envoie une requête "Succès" (Webhook) à votre backend.
- Étape E : La Mise à jour. Votre backend passe le profil de l'artisan en "Premium" dans la base de données (PostgreSQL) et recharge ses droits dans le cache (Redis).

4. Le Déblocage en Temps Réel (La Magie du Push)
C'est ici que l'expérience utilisateur devient excellente. L'artisan ne devrait pas avoir à rafraîchir l'application ou à cliquer sur un bouton "J'ai payé, vérifiez".
- Utilisation des WebSockets ou de Firebase : Dès que votre backend reçoit le Webhook de confirmation de paiement (Étape D), il pousse un événement en temps réel 
à l'application mobile (via Firebase Cloud Messaging ou une base de données temps réel).
- Reprise automatique : L'application mobile, recevant ce signal, fait disparaître le Paywall de l'écran avec une belle animation, et renvoie automatiquement 
la question (celle de l'étape 2) vers l'IA. L'artisan voit la réponse commencer à s'écrire presque immédiatement après avoir validé son paiement Mobile Money.

5. Gestion des Frictions (Edge Cases)
- Paiement échoué ou annulé : Si l'artisan n'a pas assez de fonds ou annule l'USSD, le paywall affiche un petit message discret ("Paiement non abouti. Réessayez.") mais reste actif.
- Problème réseau après paiement : Si l'artisan paie mais perd la connexion, l'historique des transactions dans la base de données est souverain. 
À sa prochaine ouverture de l'application, l'API vérifiera qu'il a bien un pass valide et l'interface sera débloquée.

Anatomie UX/UI de cet écran (Pourquoi ces choix ?)
1. La Préservation du Contexte (L'arrière-plan)
Remarquez que la question de l'artisan (sur les fondations à Bingerville) reste bien visible en arrière-plan. 
L'indicateur de chargement (⏳ Recherche...) montre que la réponse existe et l'attend. Cela crée un léger "FOMO" (la peur de manquer l'information) 
qui incite à l'achat.

2. Le Copywriting Empathique
Le texte "C'est une excellente question technique !" valorise l'utilisateur. On ne le blâme pas d'avoir épuisé son quota, 
on le félicite pour son utilisation pertinente de l'outil.

3. La Hiérarchie des Offres
Le Pass 24H (Le produit d'appel) : À 500 FCFA, c'est un achat d'impulsion indolore. Un artisan bloqué sur un chantier paiera ce montant sans hésiter 
pour gagner du temps. Le Pass Mensuel (La rétention) : Affiché juste en dessous, il sert d'ancrage de prix (3000 FCFA pour 30 jours semble très rentable 
par rapport à 500 FCFA pour 1 jour).

4. La Réassurance Mobile Money
L'intégration visuelle des logos familiers des opérateurs de Côte d'Ivoire (Wave, Orange Money, etc.) juste au-dessus du bouton de paiement dissipe les craintes liées à la sécurité.

5. L'Échappatoire (Soft Exit)
Le lien discret "Non merci, plus tard" permet de fermer la fenêtre modale sans frustration. L'artisan reste dans l'application, et le système lui suggèrera 
de payer plus tard lorsqu'il tentera une nouvelle question.

VI- Les Règles de Sécurité du Webhook (Crucial)
Vous ne devez jamais faire confiance aveuglément à une requête qui arrive sur votre webhook. Un utilisateur malveillant pourrait simuler une requête pour se 
donner un accès Pro gratuit. Pour contrer cela, on utilise une Signature HMAC :
Lors de la création de votre compte chez l'agrégateur de paiement, celui-ci vous donne une Clé Secrète (Secret Key).
À chaque paiement, l'agrégateur hache les données de la transaction avec cette clé et envoie ce "sceau" dans les en-têtes HTTP (Headers).
Votre serveur refait le même calcul. Si les deux sceaux correspondent, le paiement est authentique.

2. La clé secrète fournie par votre opérateur Mobile Money (ex: CinetPay/Wave)
PAYMENT_SECRET_KEY = os.getenv("MOBILE_MONEY_SECRET_KEY", "votre_cle_secrete_super_longue")

@app.post("/api/webhooks/mobile-money")
async def handle_payment_webhook(
    request: Request,
    x_signature: str = Header(None) # L'en-tête contenant la signature de l'opérateur
):
    # 1. Lire le corps de la requête (le Payload)
    payload = await request.body()
    
    # 2. Vérifier la signature HMAC (Sécurité anti-fraude)
    if not x_signature:
        raise HTTPException(status_code=401, detail="Signature manquante")
        
    expected_signature = hmac.new(
        key=PAYMENT_SECRET_KEY.encode('utf-8'),
        msg=payload,
        digestmod=hashlib.sha256
    ).hexdigest()
    
    if not hmac.compare_digest(expected_signature, x_signature):
        raise HTTPException(status_code=403, detail="Signature invalide. Tentative de fraude.")

    # 3. Analyser les données du paiement
    data = json.loads(payload)
    transaction_id = data.get("transaction_id")
    statut = data.get("status") # Ex: "ACCEPTED", "REFUSED"
    user_id = data.get("metadata", {}).get("user_id")
    type_pass = data.get("metadata", {}).get("type_pass") # "pass_24h" ou "pass_mois"

    # 4. Logique Métier (Si le paiement est un succès)
    if statut == "ACCEPTED":
        print(f"Paiement validé pour l'utilisateur {user_id} - {type_pass}")
        
        # A. Calculer la nouvelle date d'expiration du quota
        now = datetime.now()
        if type_pass == "pass_24h":
            date_fin = now + timedelta(days=1)
        elif type_pass == "pass_mois":
            date_fin = now + timedelta(days=30)
            
        # B. Mettre à jour la base de données (PostgreSQL) et le cache (Redis)
        # update_user_premium_status(user_id, date_fin)
        
        # C. Déclencher le déblocage en temps réel sur le mobile de l'artisan
        # (Via WebSocket ou Firebase Cloud Messaging)
        # push_realtime_unlock_event(user_id=user_id, status="UNLOCKED")
        
        return {"status": "success", "message": "Compte mis à jour"}

    elif statut == "REFUSED":
        # Gérer l'échec (fonds insuffisants, annulation)
        # push_realtime_unlock_event(user_id=user_id, status="FAILED")
        return {"status": "ignored", "message": "Paiement refusé"}

    return {"status": "ignored", "message": "Statut inconnu"}

4. Gérer la Résilience du Webhook
Les réseaux peuvent être capricieux. Voici les règles d'or pour un webhook de paiement :
- Réponse ultra-rapide (200 OK) : Votre serveur doit répondre immédiatement à l'opérateur pour dire "J'ai bien reçu l'info". 
Les traitements lourds (comme l'envoi d'un email de facture) doivent être faits de manière asynchrone (ex: via Celery ou Redis Queue). 
Si le serveur tarde à répondre, l'opérateur pensera que votre serveur est en panne et renverra le webhook en boucle.
- Idempotence : L'opérateur peut parfois envoyer le même webhook de succès deux fois par erreur. Votre code doit vérifier dans la base de données si 
la transaction_id a déjà été traitée, pour ne pas rajouter deux fois 30 jours d'abonnement au lieu d'un.

VII- Configuration de Redis 
La gestion des quotas est une étape technique fondamentale. Redis est une base de données en mémoire, ce qui signifie qu'elle est extrêmement rapide 
(temps de réponse de l'ordre de la milliseconde). C'est parfait pour vérifier les droits d'un utilisateur à chaque fois qu'il tape une touche sans ralentir 
l'application.
Voici comment structurer ce gestionnaire de quotas (Rate Limiter) pour soutenir le modèle Freemium (Questions gratuites vs Pass Pro).

1. La Stratégie des Clés Redis (Key Design)
Pour chaque artisan, nous allons utiliser deux types de clés dans Redis :
- La Clé "Premium" : artisan:{id}:premium_until
Valeur : Le timestamp (date exacte en secondes) de la fin de son abonnement.
Logique : Si cette clé existe et que sa valeur est dans le futur, l'artisan a un Pass actif. On ne décompte aucune question.
- La Clé "Freemium" : artisan:{id}:questions_gratuites:{date_du_jour}
Valeur : Un compteur (entier) du nombre de questions posées aujourd'hui.
Logique : On incrémente cette valeur à chaque question. Si elle dépasse 5, on bloque avec le statut HTTP 402 (celui qui déclenche votre Paywall).
Astuce technique (TTL) : Cette clé recevra un "Time-To-Live" (durée de vie) pour s'autodétruire tous les soirs à minuit.

2. Le Script du Gestionnaire de Quotas (Python / Redis)
Voici l'implémentation du gestionnaire qui pourras être utiliser comme "Dépendance" ou "Middleware" dans l' API FastAPI.

Python
import redis
import time
from datetime import datetime
from fastapi import HTTPException

# Connexion à Redis (à adapter selon votre environnement)
redis_client = redis.Redis(host='localhost', port=6379, db=0, decode_responses=True)

# Configuration de la limite gratuite
MAX_QUESTIONS_GRATUITES_PAR_JOUR = 5

class QuotaManager:
    @staticmethod
    def _get_midnight_seconds():
        """Calcule le nombre de secondes restantes avant minuit pour le TTL."""
        now = datetime.now()
        midnight = datetime(now.year, now.month, now.day, 23, 59, 59)
        return int((midnight - now).total_seconds())

    @staticmethod
    def verifier_droits_artisan(user_id: str):
        """
        Vérifie si l'artisan a le droit de poser une question à l'IA.
        Soulève une erreur HTTP 402 s'il doit payer.
        """
        # 1. Vérification du statut Premium (Le plus rapide)
        premium_key = f"artisan:{user_id}:premium_until"
        premium_until = redis_client.get(premium_key)
        
        if premium_until and float(premium_until) > time.time():
            # L'artisan a un abonnement valide, on le laisse passer
            return {"statut": "premium", "message": "Pass actif"}

        # 2. Gestion du Quota Gratuit
        today_str = datetime.now().strftime("%Y-%m-%d")
        quota_key = f"artisan:{user_id}:questions_gratuites:{today_str}"

        # On incrémente le compteur de manière atomique (INCR)
        # Si la clé n'existe pas, Redis la crée et la met à 1.
        questions_posees = redis_client.incr(quota_key)

        # Si c'est la première question de la journée, on configure l'autodestruction à minuit
        if questions_posees == 1:
            redis_client.expire(quota_key, QuotaManager._get_midnight_seconds())

        # 3. Vérification du dépassement
        if questions_posees > MAX_QUESTIONS_GRATUITES_PAR_JOUR:
            # On empêche le compteur de grimper indéfiniment si le front-end bug
            redis_client.decr(quota_key) 
            
            # On déclenche le PAYWALL (Erreur HTTP 402)
            raise HTTPException(
                status_code=402,
                detail={
                    "code": 402,
                    "message": "Quota gratuit épuisé. Passez à la version Pro.",
                    "offres_disponibles": [
                        {"id": "pass_24h", "nom": "Pass 24H Urgence", "prix": 500},
                        {"id": "pass_mois", "nom": "Pass Mensuel Pro", "prix": 3000}
                    ]
                }
            )

        # Il reste des crédits gratuits
        questions_restantes = MAX_QUESTIONS_GRATUITES_PAR_JOUR - questions_posees
        return {
            "statut": "freemium", 
            "restantes": questions_restantes
        }

    @staticmethod
    def activer_pass_premium(user_id: str, jours_validite: int):
        """
        Appelé par le Webhook Mobile Money quand un paiement est réussi.
        """
        premium_key = f"artisan:{user_id}:premium_until"
        
        # Calcul du nouveau timestamp d'expiration
        fin_timestamp = time.time() + (jours_validite * 24 * 3600)
        
        # Mise à jour dans Redis
        redis_client.set(premium_key, fin_timestamp)
        return True

Pourquoi cette approche est-elle robuste ?
L'atomicité de INCR : Même si un utilisateur a une mauvaise connexion et clique 4 fois très vite sur le bouton "Envoyer", l'opération INCR de Redis est atomique. 
Il ne pourra jamais tricher sur le compteur de questions posées.
- Tolérance aux pannes : Si le serveur PostgreSQL redémarre ou subit un pic de charge, Redis, lui, reste en ligne et continue de filtrer les requêtes en bloquant ceux qui ne paient pas.
- Nettoyage automatique : Grâce à expire(), vous n'avez pas besoin de créer un script lourd qui tourne toutes les nuits à minuit pour remettre les compteurs gratuits à zéro dans la base de données. Redis s'en occupe tout seul.

VIII -Intégration des WebSockets (ou d'une solution temps réel)

Dans notre architecture, le temps réel a deux missions critiques :
- L'effet "Machine à écrire" (Streaming) : Afficher la réponse de l'IA mot par mot pour éviter que l'artisan n'attende 10 secondes devant un écran vide.
- Le "Magic Unlock" (Déblocage Paywall) : Faire disparaître instantanément le mur de paiement dès que l'API Mobile Money valide la transaction, sans que l'utilisateur n'ait à rafraîchir l'écran.

Voici comment implémenter cette communication bidirectionnelle entre votre Backend (FastAPI) et votre Frontend mobile (ex: Flutter).

1. Le Gestionnaire de WebSockets (Backend FastAPI)
Il faut créer un "Manager" qui va garder en mémoire les connexions actives. Ainsi, quand le webhook de paiement reçoit une confirmation pour l'artisan "1234", 
il sait exactement sur quel "tuyau" envoyer le signal de déblocage.

Python
from fastapi import FastAPI, WebSocket, WebSocketDisconnect
from typing import Dict
import json

app = FastAPI()

class ConnectionManager:
    def __init__(self):
        # Dictionnaire pour stocker : { "user_id": WebSocket }
        self.active_connections: Dict[str, WebSocket] = {}

    async def connect(self, websocket: WebSocket, user_id: str):
        await websocket.accept()
        self.active_connections[user_id] = websocket
        print(f"Artisan {user_id} connecté au WebSocket.")

    def disconnect(self, user_id: str):
        if user_id in self.active_connections:
            del self.active_connections[user_id]
            print(f"Artisan {user_id} déconnecté.")

    async def send_personal_message(self, message: dict, user_id: str):
        """Envoie un message JSON à un utilisateur précis."""
        if user_id in self.active_connections:
            websocket = self.active_connections[user_id]
            await websocket.send_json(message)

manager = ConnectionManager()

  final ScrollController _scrollController = ScrollController();

  bool _showPaywall = false;
  bool _isGenerating = false;

  @override
  void initState() {
    super.initState();
    _connectWebSocket();
  }

  void _connectWebSocket() {
    // Remplacer par l'URL de votre backend FastAPI
    _channel = WebSocketChannel.connect(
      Uri.parse('ws://votre-api.com/ws/chat/${widget.userId}'),
    );

    _channel.stream.listen(
      (message) {
        final data = jsonDecode(message);
        _handleServerEvent(data);
      },
      onDone: () {
        // Logique de reconnexion à ajouter ici
        print("WebSocket déconnecté");
      },
      onError: (error) => print("Erreur WS: $error"),
    );
  }

  void _handleServerEvent(Map<String, dynamic> data) {
    if (data['type'] == 'stream') {
      // Effet machine à écrire : on ajoute le bout de texte au dernier message de l'IA
      setState(() {
        if (_messages.isNotEmpty && !_messages.last.isUser) {
          _messages.last.text += data['chunk'];
        } else {
          // Si c'est le premier mot, on crée la bulle de l'IA
          _messages.add(ChatMessage(text: data['chunk'], isUser: false));
        }
      });
      _scrollToBottom();
    } 
    else if (data['type'] == 'payment_required') {
      // Le quota est épuisé, on affiche le paywall
      setState(() {
        _showPaywall = true;
        _isGenerating = false;
      });
    } 
    else if (data['type'] == 'payment_success' && data['action'] == 'unlock_ui') {
      // Le webhook a validé le Mobile Money, on cache le paywall !
      setState(() {
        _showPaywall = false;
      });

        const SnackBar(content: Text('Pass Pro activé ! Reprise de la réponse...')),
      );

      _isGenerating = true; // Affiche un indicateur de chargement

    _textController.clear();
    _scrollToBottom();

          curve: Curves.easeOut,
        );

    });

- L'artisan pose une question : La fonction _sendMessage envoie le texte au format JSON via le WebSocket et fait défiler la vue vers le bas.
- L'IA répond (Succès) : Le backend envoie des morceaux de texte. La condition data['type'] == 'stream' s'active, et setState ajoute les caractères au fur et à mesure dans la bulle grise, créant une animation naturelle.
- L'IA bloque (Paywall) : Le backend renvoie payment_required. La condition déclenche _showPaywall = true. L'écran s'assombrit légèrement et la carte d'achat surgit du bas de l'écran, tandis que la question de l'artisan reste visible derrière.
- L'Artisan paie : Dès que le webhook backend valide le Mobile Money, il pousse un événement payment_success dans le WebSocket. L'application le capte, passe _showPaywall à false, et la carte disparaît instantanément.

La mécanique derrière ce code
- Le RunnablePassthrough : Dans LCEL, RunnablePassthrough() indique à LangChain que la donnée entrante dans la chaîne (ici, la question envoyée dans chain.astream(question)) doit être injectée directement dans le paramètre {question} du prompt.
- L'itérateur async for chunk in ... : Au lieu d'attendre 10 secondes que GPT-4o-mini finisse sa phrase, FastAPI réceptionne les mots (tokens) au rythme où OpenAI les calcule (environ 40 à 60 mots par seconde).
- Le non-blocage (asyncio) : Pendant que votre serveur attend le prochain mot d'OpenAI, grâce à l'asynchrone, il peut s'occuper de répondre aux WebSockets de 500 autres artisans connectés en même temps, ce qui rend votre architecture extrêmement scalable et économe en ressources serveur.

XII- Structuration de la base de connaissances pour optimiser le modèle RAG (Retrieval-Augmented Generation).

1. L'Architecture de la Base Vectorielle
Au lieu de créer une base de données séparée pour chaque métier (ce qui serait coûteux et complexe à maintenir), 
la meilleure approche consiste à utiliser un Index Unique avec Filtrage par Métadonnées (Metadata Filtering).
Chaque morceau de texte (ou "Chunk") stocké dans la base possèdera une "carte d'identité" sous forme de métadonnées.

Exemple de Métadonnées (Taxonomie)
Chaque document vectorisé devra être accompagné d'un fichier JSON structurant son contexte :

JSON
{
  "secteur_id": "artisanat_art",
  "metier_id": "maroquinerie",
  "categorie_competence": "finition",
  "type_document": "fiche_technique",
  "titre_source": "Guide pratique du travail du cuir",
  "niveau_expertise": "intermediaire",
  "mots_cles": ["cuir", "tannage", "teinture", "finition"]
}
Pourquoi c'est crucial ? Lorsqu'un utilisateur pose une question, le backend récupère son metier_id depuis son profil (ex: maroquinerie) et applique un pré-filtre strict ("Ne cherche QUE dans les vecteurs où metier_id = maroquinerie"). Le LLM n'a ainsi accès qu'aux informations pertinentes pour ce métier précis.

2. La Stratégie de Découpage (Chunking)
Un manuel PDF de 200 pages ne peut pas être envoyé d'un coup au LLM. Il faut le découper en petits blocs ("chunks") de texte. 
Pour des fiches techniques artisanales, il faut éviter le découpage aveugle au nombre de caractères. Privilégiez le Chunking Sémantique ou Structurel :
- Mauvais découpage : Couper le texte tous les 500 mots. Cela risque de couper une étape de fabrication en plein milieu ("Étape 3 : Appliquez le vernis puis... [FIN DU CHUNK]").
- Bon découpage : Découper par sections logiques (Titres, Sous-titres, Paragraphes). Un "chunk" doit contenir une idée ou une méthode complète (ex: Tout le paragraphe sur le dosage du ciment hydrofuge en maçonnerie).
Conseil : Gardez une taille de chunk d'environ 500 à 1000 "tokens" et prévoyez un chevauchement (overlap) de 10% à 15% entre deux chunks pour ne pas perdre le contexte.

3. Typologie des Données à Ingester
Pour que l'IA soit perçue comme un véritable "Copilote Expert", la base doit contenir des documents variés et qualitatifs, classés par type_document :
Les Normes et DTU (Documents Techniques Unifiés) : Les règles de l'art (sécurité électrique, normes de construction, résistance des matériaux).
- Guides de Bonnes Pratiques : Techniques de base et avancées (ex: techniques d'assemblage en menuiserie, préparation des supports en peinture).
- Fiches Produits/Matériaux : Caractéristiques des intrants (temps de séchage d'une colle, types de bois, spécificités des tissus).
- Dépannage & Résolution de problèmes (Troubleshooting) : Formats "Problème -> Cause -> Solution" (ex: "Pourquoi mon enduit fissure-t-il au séchage ?").
- Guides de Gestion & Stratégie : Comment chiffrer un devis, comment gérer sa relation client, ou comprendre les possibilités d'accompagnement financier (microfinance).

4. Le Flux d'Exécution du RAG (Comment l'IA utilise la base)
Voici ce qui se passe techniquement en une fraction de seconde lorsqu'un artisan interroge l'application :
- La Requête : Un maçon sur un chantier ouvre l'application et demande : "Quel dosage de ciment dois-je utiliser pour une fondation en zone très humide ?"
- Enrichissement (Backend) : Votre API reçoit la question. Elle identifie que l'utilisateur a le metier_id = maconnerie.
- Recherche Vectorielle (Pinecone / Qdrant) : La base vectorielle applique le filtre métadonnée : metier_id == maconnerie.
Elle compare l'embedding de la question avec la base et trouve les 3 "chunks" de texte les plus pertinents parlant des dosages pour fondations humides.
- Construction du Prompt Système : Le backend crée un prompt caché pour le LLM : "Tu es un expert en maçonnerie. 
Réponds à la question de l'artisan en utilisant uniquement le contexte suivant. Si l'information n'y est pas, dis que tu ne sais pas."
- Contexte récupéré : [Texte du chunk 1], [Texte du chunk 2]
- Question : Quel dosage de ciment...
- Génération (OpenAI / Claude) : Le LLM rédige la réponse structurée et l'envoie sur le mobile de l'artisan.

5. Maintenir et Améliorer la Base (Feedback Loop)
L'avantage de cette architecture SaaS est que l'outil s'améliore avec le temps :
- Le bouton "Pouce en l'air / Pouce en bas" : À chaque réponse, l'artisan peut noter la qualité. Si une réponse est mal notée, 
votre équipe technique peut consulter le log pour voir quels documents (chunks) ont été utilisés par l'IA et corriger la base de connaissances 
si elle est obsolète ou erronée.
- Mise à jour granulaire : Si une norme change (ex: nouvelle norme électrique), vous n'avez pas besoin de réentraîner l'IA. 
Il suffit de supprimer l'ancien document vectorisé de la base et d'uploader le nouveau. L'IA sera instantanément à jour.

XIV - Modème de prompt Système IA
Le prompt système (System Prompt) est le "cerveau comportemental" de votre IA. 
C'est le texte caché qui est envoyé au LLM avant même la question de l'artisan. 
Il définit son identité, son ton, et surtout, ses limites (les fameux garde-fous pour éviter les hallucinations).
Dans le cadre d'une architecture RAG stricte (où l'IA doit se baser uniquement sur vos documents), le prompt doit être autoritaire.

- Le Prompt Système (À intégrer dans le Backend)
Plaintext
Tu es l'Assistant Expert de ProsArtisan, le copilote technique dédié aux artisans professionnels (maçons, maroquiniers, menuisiers, plombiers, etc.). 
Ton rôle est de fournir des réponses techniques, précises et directement applicables sur le terrain, en te basant EXCLUSIVEMENT sur les documents techniques fournis.

=== RÈGLES STRICTES DE GÉNÉRATION (Garde-fous) ===
1. FIDÉLITÉ AU CONTEXTE : Tu dois formuler ta réponse UNIQUEMENT à partir des informations contenues dans le bloc <CONTEXTE> ci-dessous. 
2. ZÉRO HALLUCINATION : Si l'information nécessaire pour répondre à la question de l'artisan ne se trouve pas dans le <CONTEXTE>, tu ne dois RIEN inventer. Réponds exactement ceci : "Les documents techniques actuels de ProsArtisan ne contiennent pas cette information spécifique pour votre métier. Souhaitez-vous reformuler votre question ?"
3. SÉCURITÉ : Si la question porte sur un domaine critique (structures porteuses, haute tension) et que le contexte manque de précisions sur les normes de sécurité, ajoute toujours un avertissement de prudence.

=== TON ET FORMATAGE ===
- Sois direct, pédagogique et respectueux. Tu t'adresses à des professionnels qui sont sur le terrain et qui ont besoin d'informations rapides.
- Utilise un vocabulaire technique approprié au métier, mais évite le jargon inutile ou trop académique.
- Structure tes réponses avec des listes à puces (-), des étapes numérotées (1, 2, 3) et du texte en gras pour mettre en évidence les dosages, les mesures ou les outils essentiels.
- Ne fais jamais de longues introductions ou de longues conclusions. Va droit au but.

=== DONNÉES DE LA REQUÊTE ===
<CONTEXTE>
{context}
</CONTEXTE>

Question de l'artisan : {question}
Pourquoi ce prompt est-il structuré ainsi ?
- L'ancrage d'identité (Tu es l'Assistant Expert de ProsArtisan) : Cela donne à l'IA un cadre professionnel. Elle ne se comportera pas comme un chatbot bavard, mais comme un outil métier.
- Le Garde-fou anti-hallucination (ZÉRO HALLUCINATION) : C'est la règle la plus importante du RAG. Sans cette directive explicite de dire "Je ne sais pas", un LLM a naturellement tendance 
à inventer une réponse plausible (mais potentiellement fausse) pour "faire plaisir" à l'utilisateur. Sur un chantier de maçonnerie ou pour une installation électrique, une information inventée peut être dangereuse.
- L'optimisation du format (TON ET FORMATAGE) : En forçant l'IA à utiliser des listes à puces et à aller "droit au but", vous économisez des tokens (donc de l'argent) à chaque réponse générée, 
tout en offrant une meilleure expérience de lecture à l'artisan sur son téléphone mobile.
- Les balises (<CONTEXTE>) : Les LLM modernes (comme GPT-4 ou Claude) comprennent extrêmement bien les balises de type XML. 
Cela permet au modèle de délimiter clairement où se trouve la vérité absolue (vos documents vectorisés) et où se trouve la question de l'utilisateur.
- Comment l'utiliser dans le code (Exemple avec LangChain)
Dans le script de génération, ce prompt sera intégré sous forme de Template dynamique :

Python
from langchain.prompts import PromptTemplate

template_prosartisan = """
Tu es l'Assistant Expert de ProsArtisan...
[... le texte du prompt ci-dessus ...]
<CONTEXTE>
{context}
</CONTEXTE>

Question de l'artisan : {question}
"""

prompt = PromptTemplate(
    template=template_prosartisan,
    input_variables=["context", "question"]
)
